# Database Design Plan

Implemented so far: everything marked Stage 1 or 2 in the [ownership table](../architecture/domain-boundaries.md). Later tables are the plan and may change as their stage is designed.

## Conventions

| Topic                  | Rule                                                                                                                                           |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Primary keys           | UUIDv7 generated by Prisma (`@default(uuid(7))`), stored as `uuid`. Time-ordered values keep B-tree inserts local.                             |
| Timestamps             | `timestamptz(6)`, in UTC.                                                                                                                      |
| Naming                 | `snake_case` tables and columns through `@@map` and `@map`. TypeScript stays `camelCase`.                                                      |
| Foreign keys           | Always explicit. `onDelete: Restrict` by default; `Cascade` only for rows with no meaning alone.                                               |
| Tenant column          | `tenant_id` on every tenant-owned table, first in composite indexes.                                                                           |
| Cross-tenant integrity | Tenant-owned children reference parents by composite key `(tenant_id, id)`, so the database rejects a row pointing at another tenant's parent. |
| JSONB                  | Only for versioned game configuration, flexible metadata and provider payloads.                                                                |
| Schema files           | One `.prisma` file per domain group in `apps/api/prisma/schema/`. ADR-009.                                                                     |
| Enums                  | Prisma enums for closed state machines. Reference tables for anything configurable.                                                            |
| Soft deletion          | Only where a lifecycle requires it (`status`, `deleted_at`). Child erasure is real deletion of personal fields.                                |

## Immutability

| Data                          | How it is enforced                                                                                       |
| ----------------------------- | -------------------------------------------------------------------------------------------------------- |
| Published content versions    | New version per change; the version row is frozen by status. Results store the version id.               |
| `audit_logs`                  | `impulse_app` has only `INSERT` and `SELECT`. `UPDATE` and `DELETE` are not granted.                     |
| Coin and XP ledgers (Stage 6) | Append-only. The balance is a projection updated in the same transaction, with a unique idempotency key. |
| `refresh_tokens`              | Never stores raw tokens, only SHA-256 hashes.                                                            |

## Migration policy

1. Generate with `prisma migrate dev --create-only`, then review the SQL.
2. Every migration that adds a tenant table also adds its RLS policy and grants in the same file. The catalog test fails otherwise.
3. Production migrations are expand-and-contract: add, backfill, switch code, then remove in a later release.
4. Migrations run as `impulse_owner`, never as the application role.
5. Reference data (roles, permissions) is synchronised by an idempotent seed that runs on every deployment.

## Scaling plan

| Concern      | Plan                                                                                                                            |
| ------------ | ------------------------------------------------------------------------------------------------------------------------------- |
| Event volume | Monthly range partitions on `game_session_events` and `learning_events`, created by the scheduler.                              |
| Reads        | Aggregation jobs write summary tables. Dashboards read summaries, not event tables.                                             |
| Connections  | One pool per process. A transaction pooler (PgBouncer in transaction mode) works because tenant settings are transaction-local. |
| Analytics    | A separate analytical store once volume justifies it; the event envelope is already suitable for export.                        |
